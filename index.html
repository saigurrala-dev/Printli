Master Architecture

The Entire Platform on One Page

Real-World Scenario

A busy commercial print shop receives hundreds of daily orders from students, corporate clients, and walk-in counter visitors. The platform coordinates everything: customers submit and configure files remotely or at the counter, the cloud coordination layer validates payments and schedules jobs, while local shop terminals manage printer queues and floor staff verify output trays before customer handover.

How It Works (Step-by-Step)
  • Actors: Customers (Web and Mobile interfaces), Merchants and Operators (Counter Dashboards), and Platform Administrators.
  • Cloud Coordination Layer: Manages account tenancy, background processing queues, dynamic completion time calculations, and encrypted file storage.
  • Local Shop Terminals: Terminal software running at the shop fetches job instructions, prefetches documents, and feeds local printer spoolers.
  • Physical Verification: Floor staff inspect print quality and authenticate customer verification codes at the collection counter.
Key Architectural Takeaways & Edge Cases

Clean architectural separation: The cloud manages business logic, authorization, dynamic pricing, and audits; local terminals handle hardware execution without network lag.

03

Order Lifecycle State Machine

Real-World Scenario

A document is submitted and paid. It moves from Created to Paid, passes automated approval rules into Queued, and begins Printing. Midway through, the printer runs out of paper (Error). The order transitions to Physical Verification so staff can count the good pages before resuming or re-routing.

How It Works (Step-by-Step)
  • Upstream States: Created → Uploaded → Configured → Payment Pending → Paid.
  • Processing States: Awaiting Approval (if rules trigger) → Approved → Queued → Resource Assigned → Printing.
  • Completion & Recovery: Print Completed or Error → Physical Verification → Ready for Pickup → Collected.
Key Architectural Takeaways & Edge Cases

Digital spooling completion is strictly distinguished from physical verification. Hardware errors never cancel orders blindly—they route through staff verification.

04

Payment Flow with Idempotent Webhooks

Real-World Scenario

A customer pays for an order during network congestion. The payment gateway triggers confirmation callbacks multiple times in rapid succession. The platform checks the unique transaction key: the first callback marks the order Paid and queues the job; subsequent duplicate callbacks are safely ignored.

How It Works (Step-by-Step)
  • Initiation: Customer creates an order; the system creates a unique transaction key and initiates checkout.
  • Callback Processing: Payment gateway dispatches payment confirmation; the platform checks the unique key in the database.
  • Automated Reconciliation: Scheduled background jobs compare gateway settlement records with platform orders to resolve drops.
Key Architectural Takeaways & Edge Cases

Guarantees zero duplicate prints and zero ghost charges under unstable mobile connections and payment gateway retry policies.

05

Order Approval Flow

Real-World Scenario

A standard 2-page document prints automatically. However, an order requesting 200 full-color brochures on heavy cardstock triggers the high-volume threshold. The order holds in Awaiting Approval until the shop manager inspects paper stock and confirms print alignment.

How It Works (Step-by-Step)
  • Rule Evaluation: Paid orders are evaluated against shop threshold rules (color requirements, high page counts, large order values).
  • Branching: Routine jobs move directly to Approved; high-risk jobs pause in Awaiting Approval.
  • Staff Action: Shop operators approve to release to the print queue or reject with an instant automated refund.
Key Architectural Takeaways & Edge Cases

Protects shop materials and prevents costly paper and toner wastage from accidental customer upload errors.

06

Print Station Architecture (Cloud vs Local)

Real-World Scenario

The cloud coordination layer handles hundreds of orders across multiple shops. Instead of transmitting heavy document files over live socket streams, the cloud sends tiny metadata job descriptors. The shop terminal uses temporary signed download tokens to stream files into local cache while the previous job is printing.

How It Works (Step-by-Step)
  • Cloud Role (What): Manages orders, tenant permissions, routing logic, dynamic completion estimates, and status storage.
  • Shop Terminal Role (How): Executes silent printing, maintains local prefetch cache (1-2 upcoming jobs), and interfaces with local queues.
  • Feedback Loop: Terminal transmits regular heartbeats, queue status, and local spool errors back to the cloud.
Key Architectural Takeaways & Edge Cases

Eliminates network latency between consecutive print jobs. The local printer never sits idle waiting on file downloads between tasks.

Print Station Device Pairing

Real-World Scenario

A shop owner installs a new computer terminal at Counter 2. In the management dashboard, they click 'Add Terminal', generating a temporary 6-digit code valid for a few minutes. Opening the terminal application on Counter 2 and entering the code exchanges it for a permanent, revocable device credential.

How It Works (Step-by-Step)
  • Code Generation: Merchant administrator requests an enrollment code from the management dashboard.
  • Credential Exchange: Shop terminal submits the code; backend validates, invalidates the code, and issues a cryptographic device token.
  • Local Storage: Credential persists securely in local browser storage; terminal begins broadcasting operational heartbeats.
Key Architectural Takeaways & Edge Cases

Eliminates manual password entry on shared floor computers. Device credentials can be revoked remotely at any moment.

08

Printer State Machine

Real-World Scenario

A printer is actively processing jobs (Busy). The paper tray empties, and staff report a paper jam (Error). The routing engine instantly stops sending new jobs to this printer, diverting queue traffic to another machine until staff reload paper and mark the unit Available.

How It Works (Step-by-Step)
  • Operational States: Offline ↔ Available ↔ Reserved ↔ Busy ↔ Error / Paused.
  • Administrative Overrides: Shop owners can place units into Maintenance or Disabled states at any time.
  • Heartbeat Failover: If a terminal disconnects or goes to sleep, its associated printers automatically switch to Offline.
Key Architectural Takeaways & Edge Cases

Routing engine only dispatches jobs to healthy, active hardware, preventing queue pileups on jammed or offline printers.

09

Smart Routing Engine

Real-World Scenario

An order requires large-format double-sided color printing. The shop has multiple machines. The routing engine checks capability matrices (filtering out black-and-white units), excludes units in maintenance, and assigns the job to the machine with the shortest estimated wait time.

How It Works (Step-by-Step)
  • Capability Matching: Matches color, paper dimensions, duplex mode, and media types against registered hardware specifications.
  • Health & Policy Validation: Excludes disabled, paused, or offline resources.
  • Ranking & Assignment: Evaluates active queue depth, hardware print speed, and priority tier to select the optimal resource.
Key Architectural Takeaways & Edge Cases

Deterministic routing guarantees that orders are directed to compatible hardware with the lowest possible customer turnaround time.

ETA Calculation and Dynamic Updates

Real-World Scenario

A customer is quoted an estimated completion time of 8–10 minutes. A large priority job ahead in the queue causes the predicted completion to slip to 22 minutes. Because the change is significant, the system automatically sends an updated completion notice to the customer's phone.

How It Works (Step-by-Step)
  • Input Metrics: Page counts in queue, hardware print speed, verification buffers, and priority status.
  • Time Window Output: Generates a realistic estimated completion range rather than a fragile exact second.
  • Dynamic Recalculation: Printer jams, reroutes, or queue depth changes trigger updates and proactive customer notifications.
Key Architectural Takeaways & Edge Cases

Dynamic completion estimates prevent counter congestion by keeping customers informed of schedule changes in real time.

Priority Service and Mid-Flight Upgrades

Real-World Scenario

A customer places a standard order with a 30-minute estimate. Five minutes later, the queue backs up. The customer selects 'Upgrade to Priority', pays the incremental difference, and their job moves ahead in the queue on a dedicated fast-track printer.

How It Works (Step-by-Step)
  • Viability Verification: Priority is offered only when a faster processing route is genuinely available.
  • Incremental Upgrade: Customers upgrading mid-queue pay only the marginal difference between standard and priority rates.
  • Revenue Allocation: The priority fee is allocated between shop earnings and platform service fees per merchant policy.
Key Architectural Takeaways & Edge Cases

Transparent monetization: priority service is never sold unless real, tangible time savings can be delivered.

Physical Verification & Printer Failure Handling

Real-World Scenario

A 60-page document jams on page 38. The local print system reports that data transfer completed, but the physical tray only contains 37 sheets. The operator counts the output pages and selects 'Resume from Page 38', printing only the remaining pages without starting over.

How It Works (Step-by-Step)
  • Verification Trigger: Print submission completion moves the order into Physical Verification.
  • Staff Inspection: Staff verify page alignment, color consistency, and sheet count.
  • Resolution Options: All Correct (issue pickup code), Partial Output (resume remaining pages), Defective (restart), or Damaged (refund).
Key Architectural Takeaways & Edge Cases

Prevents extensive consumable wastage by relying on physical tray inspection as the authoritative ground truth.

File Delivery and Prefetch (Keeping it Fast)

Real-World Scenario

A print shop has a queue of 10 consecutive jobs. While Job #1 is physically printing on the paper tray, the terminal background worker prefetches Jobs #2 and #3. When Job #1 finishes, Job #2 begins printing in a fraction of a second without waiting for a download.

How It Works (Step-by-Step)
  • Direct Cloud Upload: Customer uploads direct to encrypted cloud storage; server prepares print-ready copy.
  • Queue Notification: Compact job token alerts terminal; terminal inspects the upcoming 1-2 jobs in queue.
  • Background Prefetch: Streams upcoming document files to local storage cache with checksum verification.
  • Offline Resilience: If internet connectivity drops momentarily, prefetched jobs continue printing without interruption.
Key Architectural Takeaways & Edge Cases

Maximum printer duty cycle: aggressive background prefetching ensures physical printers never sit idle waiting on network downloads.
