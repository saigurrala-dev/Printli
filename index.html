Master Architecture

The Entire Platform on One Page

Architecture & Workflow Explanation

Overview: This diagram traces the full end-to-end data boundary from human stakeholders to cloud computing and physical hardware execution.

  • Left (People & Interfaces): Customers submit orders via Web/QR or Mobile; shop staff manage queues; platform administrators oversee health and dispute resolution.
  • Middle (Cloud Logic): The cloud gateway handles authentication, tenant validation, order management, payment webhooks, dynamic routing, and WebSocket event publishing.
  • Right (Local Execution & Physical Reality): The Web Print Station runs locally on shop PCs, prefetches files via signed URLs, feeds the Windows Spooler, and triggers staff physical verification prior to secure OTP pickup.

Order Lifecycle State Machine

Explanation & Design Rationale

Separation of Concerns: Payment, Approval, Print Execution, and Physical Verification are discrete states. If a printer encounters a paper jam or hardware failure (ERROR), the order moves into PHYSICAL_VERIFICATION where staff count what was printed before retrying or re-routing.

UPLOADED --> CONFIGURED

PAYMENT_PENDING --> PAID

PAID --> APPROVED: auto print
AWAITING_APPROVAL --> APPROVED
AWAITING_APPROVAL --> CANCELLED: rejected, refund
APPROVED --> QUEUED
QUEUED --> RESOURCE_ASSIGNED
RESOURCE_ASSIGNED --> PRINTING
PRINTING --> PRINT_COMPLETED
PRINTING --> ERROR
ERROR --> PHYSICAL_VERIFICATION
PRINT_COMPLETED --> PHYSICAL_VERIFICATION
PHYSICAL_VERIFICATION --> READY_FOR_PICKUP

PHYSICAL_VERIFICATION --> CANCELLED: cancel, refund
READY_FOR_PICKUP --> COLLECTED
COLLECTED --> [*]

Payment Flow with Idempotent Webhooks

Explanation & Design Rationale

Idempotency & Reconciliation: Payment gateway webhooks frequently retry. Each payment event contains an idempotency key to prevent double charging and duplicate order creation. A background reconciliation cron job detects any unpaid drops or orphan settlements.

sequenceDiagram
participant Cu as Customer
participant API as Platform API
participant GW as Payment Gateway
participant DB as PostgreSQL
Cu->>API: Pay for order
API->>DB: Create payment PENDING with idempotency key
API->>GW: Create payment
GW-->>Cu: UPI payment screen
GW->>API: Webhook payment success
API->>DB: Event already processed?
alt Duplicate
 API-->>GW: 200 OK, ignore
else New
 API->>DB: Mark PAID, move order to approval flow
 API-->>GW: 200 OK
end
Note over API,DB: A reconciliation job compares gateway records with the DB and fixes paid-but-no-order cases

08

Printer State Machine

Explanation & Design Rationale

Health & Policy Gating: A printer is only eligible to receive new orders when it is AVAILABLE (healthy heartbeat, no active error, enabled by merchant policy). Mid-job failures pause the machine to prevent duplicate print collisions.

stateDiagram-v2
[*] --> OFFLINE
OFFLINE --> AVAILABLE: Print Station online and printer enabled
AVAILABLE --> RESERVED: job assigned
RESERVED --> BUSY: printing starts
BUSY --> AVAILABLE: done and verified
BUSY --> ERROR: staff reports jam or no paper, or station error
ERROR --> AVAILABLE: cleared
AVAILABLE --> PAUSED: staff pause
PAUSED --> AVAILABLE
AVAILABLE --> MAINTENANCE: owner policy
MAINTENANCE --> AVAILABLE
AVAILABLE --> OFFLINE: heartbeat lost
AVAILABLE --> DISABLED: owner disables
DISABLED --> AVAILABLE
