Master Architecture

The Entire Platform on One Page

Real-World Scenario

A busy college-town print shop receives 200 daily orders from university students, local businesses, and walk-in counter visitors. The platform coordinates everything: students upload files from dorms or scan counter QR codes, the cloud brain validates payments and schedules queues, while local PCs inside the shop silently feed physical printers and staff verify completed trays before handover.

How It Works (Step-by-Step)
  • Actors: Customers (Web/Mobile), Merchants/Staff (Counter Dashboards), and Platform Golden Admins.
  • Cloud Decision Engine: Manages API tenancy, BullMQ queues, dynamic ETA calculations, and document object storage.
  • Local Shop Execution: Web Print Station running in a dedicated browser window pulls job tokens, prefetches PDFs, and spools to local Windows printers.
  • Physical Verification: Floor staff inspect output quality and verify customer OTP/QR codes at the pickup counter.
Key Architectural Takeaways & Edge Cases

Clean architectural boundary: Cloud manages business logic, authorization, dynamic pricing, and audits; local hardware stations handle physical OS spooler execution without network lag.

03

Order Lifecycle State Machine

Real-World Scenario

A 100-page project report is uploaded and paid. It moves from CREATED to PAID, passes approval rules to QUEUED, and starts PRINTING. Midway through page 40, the printer runs out of toner (ERROR). The system moves the order to PHYSICAL_VERIFICATION so staff can count the good pages before resuming or re-routing.

How It Works (Step-by-Step)
  • Upstream States: CREATED → UPLOADED → CONFIGURED → PAYMENT_PENDING → PAID.
  • Processing States: AWAITING_APPROVAL (if rules trigger) → APPROVED → QUEUED → RESOURCE_ASSIGNED → PRINTING.
  • Failure & Completion: PRINT_COMPLETED or ERROR → PHYSICAL_VERIFICATION → READY_FOR_PICKUP → COLLECTED.
Key Architectural Takeaways & Edge Cases

Digital spooling completion is strictly distinguished from physical verification. System failures never cancel orders blindly—they route through staff verification.

04

Payment Flow with Idempotent Webhooks

Real-World Scenario

A customer pays ₹80 on UPI during network congestion. The payment gateway triggers the callback webhook 3 times in 4 seconds. The platform checks the database idempotency key: the first callback marks the order PAID and queues the job; subsequent duplicate callbacks return 200 OK without double-spooling.

How It Works (Step-by-Step)
  • Initiation: Customer creates order; API generates an idempotency key and initiates gateway payment session.
  • Webhook Ingestion: Gateway dispatches success webhook; API checks idempotency key in PostgreSQL.
  • Reconciliation Fallback: Background worker compares gateway settlement logs with database orders to resolve any dropouts.
Key Architectural Takeaways & Edge Cases

Zero duplicate prints and zero ghost charges under flaky mobile networks and aggressive payment gateway retry policies.

Order Approval Flow

Real-World Scenario

A standard ₹10 2-page syllabus prints automatically. However, an order requesting 200 glossy full-color wedding invites (₹4,500) triggers the 'High Value & Bulk Color' threshold. The order pauses in AWAITING_APPROVAL until the shop manager inspects paper stock and confirms alignment.

How It Works (Step-by-Step)
  • Trigger Check: Paid orders are evaluated against shop threshold rules (color, large page count, high value, special paper).
  • Branching: Standard jobs move directly to APPROVED; high-risk jobs hold in AWAITING_APPROVAL.
  • Staff Action: Owner/Operator approves to release to queue or rejects with automated instant customer refund.
Key Architectural Takeaways & Edge Cases

Prevents catastrophic paper/toner wastage from incorrect customer uploads (e.g. accidental 500-page blank document submissions).

Print Station Architecture (Cloud vs Local)

Real-World Scenario

The cloud backend handles 300 orders across 15 shops. Instead of sending heavy 40MB PDF files over WebSockets, the cloud sends tiny 1KB JSON job descriptors. The shop PC's browser Print Station uses a short-lived presigned URL to stream the PDF directly into local memory/cache while the previous job is printing.

How It Works (Step-by-Step)
  • Cloud Responsibility (What): Orders, tenancy, routing logic, dynamic ETA estimation, status persistence.
  • Local PC Responsibility (How): Silent print execution, local prefetch cache (1-2 upcoming jobs), Windows spooler interface.
  • Feedback Loop: Station transmits regular heartbeats, queue status, and local spool errors back to cloud.
Key Architectural Takeaways & Edge Cases

Eliminates network latency between consecutive print jobs. The local printer never waits on file downloads between pages.

Print Station Device Pairing

Real-World Scenario

A shop owner installs a new PC at Counter 2. In the Merchant Web Dashboard, they click 'Add Station', generating a 6-digit one-time code valid for 10 minutes. Opening the Print Station URL on Counter 2 and entering the code exchanges it for a persistent, cryptographically signed device token.

How It Works (Step-by-Step)
  • Code Generation: Merchant Admin requests pairing code from Backend via authenticated dashboard session.
  • Exchange: Shop PC submits code to Backend; Backend validates, invalidates the code, and issues a revocable Device Credential.
  • Storage: Token persists in the browser profile (IndexedDB); station immediately begins sending telemetry heartbeats.
Key Architectural Takeaways & Edge Cases

Zero manual credential sharing or insecure password entry on floor PCs. Device credentials can be revoked remotely at any moment.

08

Printer State Machine

Real-World Scenario

Printer 2 is actively printing (BUSY). The paper tray runs out of sheets. Staff report a paper jam (ERROR). The routing engine instantly stops routing new jobs to Printer 2, diverting queue traffic to Printer 1 until staff reload paper and mark Printer 2 back to AVAILABLE.

How It Works (Step-by-Step)
  • Operational States: OFFLINE ↔ AVAILABLE ↔ RESERVED ↔ BUSY ↔ ERROR / PAUSED.
  • Administrative Overrides: Owners can set policy overrides (MAINTENANCE, DISABLED) at any time.
  • Heartbeat Failover: If the PC browser tab sleeps or loses connection, the resource automatically transitions to OFFLINE.
Key Architectural Takeaways & Edge Cases

Routing engine only dispatches jobs to healthy, policy-enabled hardware, preventing queue pileups on jammed or offline printers.

09

Smart Routing Engine

Real-World Scenario

An order requires A3 Double-Sided Color Glossy. The shop has 4 printers. The routing engine checks capability matrices (eliminating B&W and A4-only printers), filters out a machine in MAINTENANCE, and assigns the job to the machine with the shortest estimated wait time.

How It Works (Step-by-Step)
  • Capability Filter: Matches color, paper size, duplex, and media type against registered hardware capabilities.
  • Policy & Health Check: Filters out disabled, paused, or offline printers.
  • Ranking & Score: Evaluates active queue length, printer speed (PPM), and priority status to compute ETA and assign.
Key Architectural Takeaways & Edge Cases

Deterministic, explainable routing with zero black-box heuristics ensures customers always receive the fastest possible turnaround.

ETA Calculation and Dynamic Updates

Real-World Scenario

A customer is quoted an 8–10 minute ETA. Suddenly, a 150-page priority job ahead in the queue causes the predicted completion to slip to 22 minutes. Because the change exceeds the 5-minute significance threshold, the system pushes an updated ETA alert to the customer's phone.

How It Works (Step-by-Step)
  • Input Metrics: Page counts ahead, PPM speed, verification buffers, priority tier weighting.
  • ETA Range Output: Generates realistic time window (e.g. 7–10 minutes) rather than an overly fragile exact second.
  • Event Recalculation: Jams, reroutes, or queue depth changes trigger recalculations and smart customer notifications.
Key Architectural Takeaways & Edge Cases

Dynamic ETA prevents crowded shop counters. Customers receive proactive delay notifications rather than waiting in uncertainty.

Priority Service and Mid-Flight Upgrades

Real-World Scenario

A student in a rush places a standard order with an ETA of 30 minutes. Five minutes later, the queue backs up. The customer taps 'Upgrade to Priority', pays an incremental fee of ₹25, and their job jumps to the head of the priority-capable printer queue.

How It Works (Step-by-Step)
  • Offer Verification: Priority is only offered if a faster routing path is mathematically achievable.
  • Incremental Upgrade: Customers who upgrade mid-flight pay only the difference between standard and priority fees.
  • Revenue Allocation: Priority surcharge is split between merchant revenue and platform fees according to shop agreement.
Key Architectural Takeaways & Edge Cases

Transparent monetization: priority is never oversold when it cannot deliver tangible time savings.

Physical Verification & Printer Failure Handling

Real-World Scenario

A 60-page PDF experiences a paper jam on page 38. The Windows print spooler shows 'Print Complete' because all bytes were sent, but the tray only has 37 physical pages. The operator counts the pages in the tray and clicks 'Resume from Page 38', finishing the job without re-printing pages 1-37.

How It Works (Step-by-Step)
  • Completion Check: Spooler submission triggers PHYSICAL_VERIFICATION state.
  • Staff Inspection: Staff verify page quality, color saturation, and total count.
  • Resolution Branches: All Correct (issue OTP), Partial Output (resume remaining pages), Defective (restart), or Jam/Damage (refund).
Key Architectural Takeaways & Edge Cases

Prevents massive consumable wastage by treating physical tray inspection as the authoritative ground truth.

Authentication and RBAC

Real-World Scenario

File Delivery and Prefetch (Keeping it Fast)

Real-World Scenario

A print shop has a queue of 10 consecutive jobs. While Job #1 is physically printing on the paper tray, the Print Station background worker prefetches Jobs #2 and #3. When Job #1 finishes, Job #2 begins printing in 0.1 seconds without waiting for a download.

How It Works (Step-by-Step)
  • Direct Cloud Upload: Customer uploads direct to encrypted S3 object storage; server prepares print-ready PDF.
  • Queue Notification: Small job token alerts station; station inspects the upcoming 1-2 jobs in queue.
  • Background Prefetch: Streams upcoming PDF files to local disk cache with SHA-256 verification.
  • Offline Resilience: If internet drops momentarily, prefetched jobs continue printing without interruption.
Key Architectural Takeaways & Edge Cases

100% printer duty cycle: aggressive background prefetching ensures physical printers never sit idle waiting on network downloads.
